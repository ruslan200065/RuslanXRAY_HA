# RuslanXRAY HA — Xray Gateway for Home Assistant OS

Экспериментальное дополнение HAOS на базе [RuslanXRAY OpenWrt](https://github.com/ruslan200065/RuslanXRAY_openwrt). Работает на **x86-64 / aarch64**, не требует Proxmox. Веб-панель на русском языке открывается через авторизованный Home Assistant Ingress.

> **Preview 0.3.11.** Локальные модульные тесты пройдены, но сборка Docker и работа на настоящем HAOS ещё не проверены. До тестирования сделайте полный бэкап и обеспечьте физический доступ к консоли. Boot установлен в manual: приложение не запускает VPN при загрузке автоматически.

## Установка из репозитория

1. В Home Assistant открыть **Настройки → Приложения / Дополнения → Магазин → ⋮ → Репозитории**.
2. Добавить `https://github.com/ruslan200065/RuslanXRAY_HA`.
3. Обновить список и установить **Ruslan Xray Gateway (Experimental)**.
4. Запустить дополнение, открыть веб-панель, загрузить полноценный JSON Xray, выбрать WAN и выделенный интерфейс клиентов.
5. Вкладка **Сеть**: выбрать `manual`, `dhcp` или `wifi_ap`, адрес шлюза и диапазон DHCP. Сохранить, нажать **Проверить и показать правила**, убедиться в правильности.
6. Только после проверки запустить шлюз, подключив один тестовый клиент к выделенному порту или дополнительному Wi-Fi адаптеру.

Для схемы `eth0 → Xray → eth1` используйте разные интерфейсы. **Нельзя выбирать рабочий интерфейс Home Assistant как клиентский:** приложение проверяет системный default route и запрещает его использовать как выход.

## Реализовано в 0.3.0

- Определение физических интерфейсов и системного default WAN, выбор выделенного интерфейса клиентов.
- Полный JSON Xray без изменения сохранённого исходного профиля, проверка бинарником Xray.
- Прозрачный IPv4 TCP/UDP TProxy, собственная таблица nftables, policy routing и блокировка прямой пересылки.
- Маршрутизация `force` на указанный Xray outbound/balancer либо `native` с сохранением исходных routing.rules. В режиме `native` правила профиля могут допускать прямой выход.
- `manual`: IP шлюза уже настроен через HAOS. `dhcp`: временный IP на выделенном Ethernet и локальный dnsmasq DHCP (без DNS-сервера на порту 53).
- `wifi_ap`: экспериментальная точка доступа на **отдельном** Wi-Fi адаптере через hostapd + DHCP, 2.4 ГГц WPA2-PSK; адаптер должен поддерживать AP mode и не быть задействован в конфигурации HAOS.
- Доступ к панели только через Ingress (входящие подключения от Supervisor), порт Ingress выбирается динамически.
- Очистка созданных маршрутов, firewall, демонов и временно назначенных IPv4 при штатном выключении.

## Текущие ограничения / безопасность

- Нет фонового автообновления подписки, отдельных Geo-обновлений, мониторинга качества и автоматического переключения серверов.
- Нет однопортового VLAN/общей сети, вход через не-default WAN, параллельной раздачи нескольким интерфейсам.
- Не реализованы маршрутизация и VPN IPv6: IPv6-транзит со стороны клиентов заблокирован. IPv6-адреса самого HAOS не меняются.
- Wi-Fi AP может не стартовать, если NetworkManager HAOS уже владеет радио или драйвер не поддерживает `nl80211` AP. Приложение **не меняет** настройки NetworkManager, не отключает системный Wi-Fi и не переключает WAN.
- DHCP-режим предполагает выделенную отдельную подсеть без других DHCP-серверов. Wi-Fi клиент → Ethernet / USB LTE как WAN в будущем, когда интерфейс WAN уже выбран системой HAOS как default route.
- Работу TProxy ограничивает наличие TProxy-поддержки в ядре HAOS, привилегий и совместимости nftables; не все комбинации оборудования протестированы.
- При аварийном завершении дополнения отдельные правила nftables могут остаться. Веб-панель позволяет удалить их вручную. Отсутствие утечек после аварийной перезагрузки HAOS не гарантируется; не используйте в критичных системах до проверки.

## Разработка

```bash
python -m unittest discover -s tests -v
```

Основные части: `xray_gateway/app/engine.py` (TProxy/маршруты), `network.py` (DHCP, AP), `server.py` (Ingress API), `index.html` (UI), `Dockerfile` (образ). Все операции запуска сетевых служб доступны только после ручного подтверждения в панели. На штатной конфигурации HAOS default route не изменяется.

## Подписка по URL (0.3.0)

В разделе **Подписка и профили** вставьте URL подписки Remnawave, при необходимости настройте User-Agent и флажок /json. Нажмите **Сохранить URL**, затем **Обновить каталог**. Дополнение создаёт постоянный X-HWID, передаёт его в заголовке запроса, принимает полный Xray JSON, массив профилей и Base64 JSON. Все конфигурации проверяются через Xray до замены каталога. Выберите профиль кнопкой и запустите шлюз. Во время обновления или смены профиля работающий шлюз должен быть остановлен. Секретный URL сохраняется с правами 0600 и не возвращается в браузер по API. Это не ограничивает чтение файла привилегированным пользователем хоста.

Ссылки vless://, hysteria2:// и не-JSON подписки пока не поддерживаются; автообновление по расписанию тоже ещё не реализовано.

## Wi-Fi 5 ГГц и страна (0.3.5)

В разделе **Сеть** можно указать фактический ISO-код страны (например, RU, FI, DE) и по желанию включить **Применять страну через iw reg set**. Без явного флажка дополнение не меняет регуляторный домен. С флажком при запуске AP программа читает исходный глобальный регион, запрашивает новый регион через iw, проверяет выбранный канал по действующим ограничениям драйвера и добавляет country_code/ieee80211d в hostapd. При остановке предпринимается попытка восстановить прежнее значение, если его не изменил другой администратор. Запрос страны действует на всю Wi-Fi подсистему HAOS; после аварийного завершения автоматическое восстановление не гарантируется.

**Важно:** выбор страны не является обходом запрета no-IR/DFS и не может снять ограничения драйвера, прошивки или self-managed адаптера. Указывайте только реально применимую страну. Если 5 ГГц остаётся недоступен, диагностируйте поле wifi.wlo1.reg_domain и флаги канала.

Появилась галочка **802.11n (HT20)**, по умолчанию включена. Это позволяет на совместимых адаптерах уйти от 11g/11a и повысить скорость. Ширина 40/80 МГц и 802.11ac пока не настраиваются. При проблемах с совместимостью можно выключить 802.11n.

## Wi-Fi каналы и выход из панели (0.3.6)

Во вкладке **Сеть → Канал Wi-Fi** доступен расширенный список основных каналов шириной 20 МГц: **1–13 (2,4 ГГц)**; **36–64, 100–144, 149–165 (5 ГГц)**. Список сверяется с выбранным радиоадаптером через `iw phy`; неподдерживаемые и отключённые аппаратно каналы помечаются и блокируются. Каналы с `no-IR` могут разблокироваться после применения реальной страны, но если драйвер self-managed продолжает запрещать AP, приложение не пытается обойти это ограничение.

**DFS**: каналы 52–64 и 100–144 имеют отдельную галочку и требуют явного разрешения, выбора реальной страны и включения применения регуляторного домена. Для них дополнение включает `ieee80211h=1` в hostapd. Перед стартом может потребоваться проверка наличия радара (CAC); запуск не гарантирован даже при выборе канала, если драйвер не поддерживает DFS AP. Проверяйте доступность по диагностике и логам hostapd. В этом релизе не добавлено управление шириной канала 40/80 МГц.

Вверху веб-интерфейса появилась кнопка-ссылка **«← Назад в Home Assistant»**, переходящая на `/` с `target="_top"` по прямому нажатию, чтобы выходить из панели дополнения. Если определённый клиент Home Assistant ограничивает навигацию из iframe, используйте стандартную боковую панель; поведение внутри мобильного приложения ещё не подтверждено.

## USB Wi-Fi Realtek RTL8851BU (0.3.8)

В раздел **USB Wi-Fi** добавлена диагностика USB-адаптера с идентификатором `0bda:b851` (Realtek RTL8851BU). Панель показывает версию ядра HAOS, наличие модуля `rtw89_8851bu`, текущие USB-интерфейсы и привязанные драйверы. Кнопка **Загрузить драйвер** выполняет только `modprobe rtw89_8851bu` и не принимает произвольные имена модулей, URLs или shell-команды.

Дополнение использует официальный механизм HAOS `kernel_modules: true` (доступ к read-only модулям ядра хоста + право загрузки) и пакет `kmod` для `modprobe/modinfo`. Доступы расширены относительно предыдущей версии, однако вручную отключать Protection Mode для этого не требуется.

**Граница возможностей:** сам модуль `.ko` в дополнение не включён: он должен быть собран для точной версии и конфигурации ядра HAOS. Если в `/lib/modules/$(uname -r)` нет `rtw89_8851bu`, контейнер не может установить его обычным `apk add` и не сможет самостоятельно создать Wi-Fi-интерфейс. В таком случае панель явно показывает статус `module_missing`; нужно добавить подходящий модуль на уровне HAOS либо использовать адаптер с поддерживаемым встроенным драйвером. Firmware также должен присутствовать в HAOS. Если интерфейс появился, выбери его в разделе **Сеть**.

Вкладка работает отдельно от работающего Xray: проверка и загрузка модуля не отключают VPN, не изменяют маршруты и не переключают WAN. Загруженный модуль остаётся в ядре после остановки дополнения и может потребовать повторной загрузки после перезагрузки хоста.

## USB Wi-Fi в userspace: этап 1 (0.3.9)

Выбран путь пользовательского драйвера **RTL8851BU (0bda:b851)** вместо загрузки `.ko` в ядро. Добавлена инфраструктура `libusb`/`PyUSB` с `usb: true` в HAOS и новая диагностика во вкладке **USB Wi-Fi**: USB-дескрипторы, конфигурации, интерфейсы и endpoint'ы. Код `usbuserspace.py` содержит API для контролируемого захвата только vendor-specific интерфейса и bulk-передачи данных. Через HTTP пока доступно **только безопасное чтение стандартных USB-дескрипторов**; интерфейсы не захватываются, прошивки не загружаются, команды Realtek не отправляются, Bluetooth не отключается.

Этап 1 НЕ создаёт виртуальный wlan-интерфейс и НЕ запускает 5 ГГц AP: требуется портировать RTL8851BU `rtw89` и реализовать подготовку чипа, загрузку firmware, 802.11 TX/RX и взаимодействие с hostapd/передачей Ethernet-трафика. `kismetwireless/userspace-wifi` использует libusb, однако официально RTL8851BU/rtw89 им не поддерживается; его HWSIM-путь также использует модуль ядра `mac80211_hwsim`. Без дополнительной разработки обещать 5 ГГц нельзя. Сохраняется существующий рабочий режим 2,4 ГГц на встроенном адаптере.

## Userspace RTL8851BU: подтверждение USB-топологии и claim/release (0.3.10)

Проверена реальная USB-дескрипторная карта `0bda:b851`: USB интерфейс **2** (`ff:ff:ff`), Bulk IN **0x84**, семь Bulk OUT **0x05, 0x06, 0x07, 0x09, 0x0a, 0x0b, 0x0c**. Bluetooth работает на отдельных интерфейсах **0/1** (`e0:01:01`) и не используется драйвером Wi-Fi.

В `app/usbuserspace.py` введён разбор WLAN интерфейсов `wlan_candidates()` по аналогии с исходниками Linux `rtw89/usb.c`. Ответ `GET /api/usb-wifi/userspace` теперь возвращает `wlan_candidates` с одним Bulk IN, перечнем Bulk OUT и `valid_rtw89_topology`.

Добавлен **строго опциональный** тест `POST /api/usb-wifi/userspace/claim-test` и кнопка «Тест захвата интерфейса №2». Операция проверяет, что USB устройство единственное и имеет ровно один совместимый интерфейс, затем вызывает `claim_interface` и `release_interface` для Wi-Fi интерфейса (не для Bluetooth). Не выполняется `set_configuration`, `detach_kernel_driver`, запись/чтение данных Bulk, загрузка прошивки или настройка радио.

**Это всё ещё НЕ Wi-Fi-драйвер**. Успешный тест доказывает только возможность пользоваться USB-интерфейсом из контейнера; для рабочего AP потребуется портировать USB control/read/write, инициализацию RTL8851B, firmware H2C/C2H, управление каналами, beacon/WPA и передачу данных. Bluetooth интерфейсы не захватываются, но тест может завершиться ошибкой, если Wi-Fi интерфейс уже занят другим процессом/драйвером.

Источники: [rtw8851bu.c](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtw89/rtw8851bu.c), [rtw89/usb.c](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtw89/usb.c).

## Userspace RTL8851BU: первый регистр (0.3.11)

После успешного теста захвата USB-интерфейса #2 доступен следующий тест **«Прочитать регистр питания RTL8851BU»**. Это реальная USB control vendor-команда, но она выполняется только по явному нажатию, **не автоматически**.

Команда реализует `rtw89_usb_vendorreq` в режиме READ по исходникам ядра Linux: `bmRequestType=0xC0`, `bRequest=0x05`, `wValue=0x0004`, `wIndex=0`, 4 байта, little-endian. Читает `R_AX_SYS_PW_CTRL` (адрес `0x0004`), показывает шестнадцатеричное значение, освобождает только WLAN USB interface #2. Не использует ни один другой адрес и не реализует произвольный register read API через HTTP. На уровне приложения **не отправляет vendor WRITE, не загружает firmware, не делает radio TX**, не захватывает Bluetooth интерфейсы 0/1 и не выполняет reset.

**Состояние:** интерфейс открыт и закрыт в тесте 0.3.10. До получения результата нового USB vendor READ не утверждать, что собственный userspace-драйвер способен управлять RTL8851BU. Успех чтения не означает возможность создать AP: оставшиеся этапы firmware/H2C/C2H/MAC/PHY/802.11 описаны в [плане](docs/RTL8851BU_USERSPACE.md).

Документация протокола: [linux/rtw89/usb.h](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtw89/usb.h), [linux/rtw89/usb.c](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtw89/usb.c), [linux/rtw89/reg.h](https://github.com/torvalds/linux/blob/master/drivers/net/wireless/realtek/rtw89/reg.h).
